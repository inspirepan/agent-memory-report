Anthropic Agent Memory：从 dreaming、知识表示与检索，到自建架构和 Claude Code 的实际配置边界。

资料核对：2026-11-07 · 研究与工程建议 · 阅读约 20 分钟

研究结论自建架构Dreaming评测产品边界Claude Code实施次序官方来源
一句话结论：记忆不是把所有对话塞进向量库，而是把可追溯的经验转化为未来可检索、可纠错、可撤销的上下文；离线整理可以提高质量，但也会引入成本和污染风险。

证据说明：本文区分 Anthropic 报告的观察与下文的自建设计建议。架构、配置与阈值均为示例，未在你的系统中部署或实测；效果、产品可用性和版本需自行验证。

01 · 原文真正说了什么

Anthropic 将 agent memory 定义为：从用户交互和任务中获得、跨会话保留、未来可读的知识。它不是模型权重更新，也不是单次会话的上下文学习；compaction 是压缩当前会话，不等于持久记忆。原文借用 dreaming 描述在交互间隙回看会话、修正记忆、建立可导航表示的离线计算。[1]

413 vs 9+1

宝可梦单次运行、约 10,000 步：Sonnet 3.7 的 413 个记忆文件与 1 枚徽章，对照 Fable 5 的 9 个文件加顶层索引与 4 枚徽章。模型不同、各一次，不能推断减少文件本身导致提升。

13% → 48%

Stainless 约 35 万文件、4.2 亿 token 语料上的 25 题评测，wiki dreaming 从 2 扩至 128 个 session，wiki-only 评分从 13% 升到 48%。不是通用生产准确率。

53% → 61%

同一企业语料，单独搜索 53%，成熟 wiki + 搜索 61%；联合检索另节省约 20,000 token/题。不同构建阶段 wiki + 搜索从 54% 增至 61%。

72% → 100%

一项法律简报任务中，原始共享表仅覆盖 57 项事实中的 41 项；改造指令、每份合同单页单写者并保留原文后，评分标准覆盖升至 100%。多项改动一起发生，不能归因于单一机制。

研究还发现：强模型在 CL-Bench 中仅获知记忆目录存在即可受益，硬性要求“只记录失败”反而削弱收益；对较旧模型，要求先读记忆并验证假设使该任务分数接近翻倍。另一项并购 24 题测试中，较依赖跨文档或判断的项目 wiki 为 87%、搜索为 73%；另一法律任务中简单单文档检索无明显收益，甚至有 wiki 大于原始文档。

边界：数字来自特定模型、数据和评分条件，部分为单次案例，缺少可推广的因果估计；wiki 构建消耗额外计算。文本记录也不是天然真相，原始会话可能同样错误。

02 · 自建系统：分层，而非一个大 prompt

交互 / 工具结果 ──→ 事件日志（可追溯、访问受控）
       │             ↓ 异步抽取 / 证据标注
       └────────→ 候选记忆 → 校验 / 审核 → 版本化记忆库
                                          ↓
请求 → 身份与权限 → 混合检索 → 重排 / 时效过滤 → 有预算的上下文
                                          ↑
              Dreaming：回放 → 纠错 → 合并 → 差异评测 → 发布 / 回滚

建议最小系统先用事务型数据库保存记录和事件，再用全文检索；只有实体规模和查询模式证明需要时再引入向量索引与 wiki。原始对话、派生事实、可执行指令必须区分信任等级；检索到的文本是数据，不是系统指令。

数据模型：每条记忆都是可治理的主张

{
  "id": "mem_…", "tenant_id": "tenant_…", "scope": "project",
  "subject": "api-tests", "claim": "集成测试需要 Redis",
  "kind": "procedure", "status": "candidate", "confidence": 0.7,
  "evidence": [{"session_id": "ses_…", "event_id": "evt_…"}],
  "observed_at": "2026-11-07T00:00:00Z", "valid_until": null,
  "version": 1, "supersedes": null, "sensitivity": "internal",
  "acl": ["project:read"], "last_verified_at": null
}

示例字段不是 Anthropic API schema。置信度是待校准的内部信号，不代表真实概率；主张、证据、权限、时间及来源版本应可单独查询。

写入与检索链路

  1. 写入：会话中保存用户明确要求记住的偏好和高价值经验，先进入 candidate；后台抽取携带来源、时间、有效域与敏感级别。敏感内容需脱敏、同意或拒绝持久化；不要把一次猜测升级为规则。
  2. 验证：对有外部事实的条目回源；存在冲突就保留双方、标记待核查，别按生成时间盲目覆盖。高风险记忆需要人工审批。
  3. 读取：先做租户与 ACL 过滤，再按任务对全文、结构化字段和语义候选混合召回；结合证据强度、关联度、时效性重排，并对变化快的事实回源验证。
  4. 注入：每次只放少量稳定索引和本任务命中记忆，附来源及时间；密钥、用户生成的恶意指令和未批准内容不得上升为系统指令。无可靠命中时明确承认不知道。
  5. 删除：支持删除、过期、撤回与传播至索引和派生 wiki；审计与备份的保留、脱敏和清除按政策实施。

并发安全：单写者只是起点

对同一实体采用分片与单写者，或版本号乐观锁（CAS），冲突则重新读取、合并、重试；数据库事务保证主记录和事件一致，异步索引用 outbox + 幂等事件恢复。离线任务基于快照生成 patch，发布时检查基线版本并对冲突逐条审阅。文件系统方案需要锁、临时文件与原子重命名；多主机共享文件系统的锁语义必须单独验证。不要让多个 agent 无保护地改同一个 Markdown 表格。

03 · Dreaming：从反思到可控发布

Dreaming 是离线巩固流水线，不是神秘的模型再训练。建议按变更频率、访问频率和风险决定触发：新近高价值事件可尽快处理，低价值或从未使用的记录不必反复扫描。

  1. 冻结输入快照：指定时间范围、来源版本、权限与预算，排除不允许处理的数据。
  2. 提取候选：回看事件找重复、矛盾、过时或缺失链接；以原文证据支持每条修改，标明未知。
  3. 输出隔离草稿：产生新增、修改、废弃及证据的 diff，禁止直接覆盖线上高风险记忆。
  4. 质量门：权限与敏感数据扫描、引用可达性、冲突检查、回归任务集；高风险变更人工审批。
  5. 原子发布版本：CAS 防止覆盖新写入，建立回滚点；监测任务成功率、错误复用与成本，异常自动停止。

原文案例中的“共同日志协调”与“每合同单页单 agent”提示，组织结构与并发机制同样影响结果。但不能把研究案例当成所有业务的最优配置。

04 · 怎样证明记忆真的有用

维度测量方法失败信号
任务价值同一任务集比较无记忆、原始检索、记忆+检索、再加 dreaming；固定模型、预算与工具。成功率无提升，或事实准确度下降。
召回与引用标注 gold 记忆，测 recall@k、引用支持率和错误引用率。召回无关信息或引用不能证明结论。
安全与时效跨租户探测、过期事实、提示注入、删除后再检索和并发覆盖测试。越权、泄露、执行恶意指令或已删除信息复现。
资源开销记录在线延迟、token、索引及 dreaming 成本，并分摊每个完成任务。收益低于额外计算和运维成本。

按用户和时间拆分训练/评测，留出未见过的会话，避免同一原文进入构建与答案集；用配对任务报告样本量和不确定性，建立人工标注一致性检查。对删除、纠错和并发做故障注入。先定业务可接受门槛，不照搬论文百分数。

05 · Memory Tool、Agent SDK、Managed Dreams 不是一回事

能力负责什么开发者责任 / 注意
Memory ToolAPI 提供工具协议；模型请求 /memories 下文件操作，应用返回 tool_result。客户端实现存储、隔离、校验和六类文件操作；需防路径穿越。不会自动提供完整 dreaming。[2]
Claude Agent SDKPython/TypeScript 中运行 Claude Code agent loop、工具、会话、hook 等。运行进程及存储生命周期由应用管理；不要把 session resume 或加载项目配置等同于已实现长期知识治理。[3]
Managed Agents / Dreams托管 harness 与 memory store；Dreams 异步读取已有 store 和 1–100 个 session，输出独立 store。Dreams 为 research preview，需申请访问；输入 store 不变，输出需审查再采用。文档注明该功能不符合 ZDR，数据保留需先核实。[4]

Memory Tool 声明示例为 {"type":"memory_20250818","name":"memory"}，还必须实现客户端 handler 与工具结果循环。Managed memory store 默认读写挂载可能被提示注入污染：应按任务使用只读和最小权限，具体以官方文档为准。[5]

06 · Claude Code：持久指令、经验和工具的分工

CLAUDE.md 是人维护的持续指导；Auto Memory 是 Claude 自动保存的经验。两者都属于上下文，不是强制安全机制。项目 CLAUDE.md 适合通用测试命令、稳定约束；不应堆积临时日志。官方建议每文件尽量低于 200 行。[6]

# CLAUDE.md（示例，按项目真实命令替换）
## 验证
- 修改 API 后运行 npm test -- api；失败不得标记完成。
- 数据迁移需列出回滚方式并由维护者审批。
## 持续上下文
- 不要把凭据写入仓库或记忆。
- 测试未执行时明确说明，不得声称通过。

Auto Memory：本地 session 默认启用，存于 ~/.claude/projects/<project>/memory/；同一仓库 worktree 通常共享、不同机器不自动共享。启动加载 MEMORY.md 前 200 行或 25KB（先到为准），主题文件按需读取。/memory 查看/编辑/开关，/context 查看已加载指令。可在项目设置写入 {"autoMemoryEnabled":false}；不同运行环境默认可能不同。

Rules：无 paths 的规则随项目加载；带 paths 的规则在匹配文件时加载。例：.claude/rules/api.md：

---
paths:
  - "src/api/**/*.ts"
---
# API 规则
- 修改接口时覆盖鉴权及非法输入测试。

Skills：把多步骤流程放在 .claude/skills/<name>/SKILL.md，可手动调用，也可由 Claude 在相关时加载；适合按需工作流，而非把所有操作放到全局上下文。[7]

---
name: review-memory
description: Review memory changes for evidence and stale claims
---
检查候选条目是否有来源、时效和权限；
输出可审核的差异，不要自行发布。

示例配置须按项目实际需求调整，并以实际 Claude Code 版本文档为准。

Subagent：独立上下文可减少主对话噪音；其 memory: project 开启项目范围的独立持久记忆，主对话 auto memory 通常不会自动注入 subagent；关闭 auto memory 时该能力不生效。[8]

# .claude/agents/memory-reviewer.md
---
name: memory-reviewer
description: 检查记忆的证据与过期风险
memory: project
---
核对来源、冲突和权限，返回待审核变更；不要自动发布。

Hooks 与 compact：需要确定执行的动作，应采用权限设置及生命周期 hooks，而不是只写提示词。PreToolUse 可在工具调用前做控制；对 shell 等复合操作，仍须配合沙箱和权限，不能将示例当作完整安全边界。/compact 和自动压缩用于释放当前会话上下文，不是长期记忆；以下示例在压缩后注入简短提醒。[9]

{
  "hooks": {
    "SessionStart": [{
      "matcher": "compact",
      "hooks": [{
        "type": "command",
        "command": "printf '提醒：修改后运行项目测试，未验证不得宣称完成。\\n'"
      }]
    }]
  }
}

以上配置为可调整示例，未在用户环境中执行；放入 .claude/settings.json 前应合并现有设置并审核 hook 命令。用 /hooks、/context 与真实任务核验，不要假定加载即遵循。

07 · 实施次序：先可恢复，再谈智能

  1. 第 1 阶段｜建立边界：定义租户、数据分类、保留期限与删除；记录事件与来源；做最小权限。
  2. 第 2 阶段｜闭环 MVP：稳定索引 + 主题记忆，人工可编辑，写入版本和证据；先做全文检索与上下文预算。
  3. 第 3 阶段｜离线治理：异步生成候选 diff，单写者/CAS、防注入检查、人审及回滚；先小流量。
  4. 第 4 阶段｜评测与扩展：建立固定任务集、分组对照、泄漏/遗忘/冲突测试；确认收益后再加入向量、wiki 和更复杂编排。
上线门槛：任何阶段只要无法回答“这条记忆来自哪里、谁能读、何时过期、如何纠正与删除”，就不该扩大自动写入范围。
